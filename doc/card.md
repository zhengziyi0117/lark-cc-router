# 卡片

`card.ts` 里三层：

- `CardBuilder`：把 `AgentEvent` 流折叠成「正文」和「过程」两段文本。**群里的卡片和 web UI 的预览走的是同一个 `CardBuilder` + `buildCard`**，预览不会跟真卡片漂移。
- `buildCard()`：按 30KB 预算把正文和过程裁好，组装成卡片 JSON。
- `CardStream` / `KitStream`：一张卡片的生命周期：什么时候开、怎么节流、收尾帧怎么保证不丢。

## 以谁的身份发

**发送、更新、撤回必须是同一个身份**：更新卡片的接口只认「消息的发送者」，实测 bot 改不了 user 发的消息（`230001 ... bot or user is not the message's sender`），反过来也一样。

所以 @我 那条路全程 `--as user`（卡片显示成「我说的」，不是机器人），@机器人 那条路全程 `--as bot`。

## @我：判明要排查才开话题

@我 的消息里大部分是闲聊。以前是先把卡片发出去、判了 SKIP 再撤回，结果每句闲聊都在群里开一个话题又收回去，比不回还吵。

现在 `CardStream` 是**懒开**的：事件从第一秒就攒着，但在 `open()` 之前一个字节都不往群里发。什么时候开由 `shouldOpenThread()` 决定：

- 模型**动了工具**：都在查代码了，肯定是排查；
- 模型**开口说了一句不是 `SKIP` 的正文**：它决定要回。

**思考不算数**：「想了一下发现是闲聊，然后输出 SKIP」是最常见的路径，在思考上开闸等于没改。代价是群里要等模型第一次开口才看到卡片，通常几秒。

收尾时还没开过：

- 有正经结论，或者跑挂了 → 补开（静默吞掉别人的 @ 更糟）；
- 判了不用回 → 永远不开，群里什么都不留。
- 真开出去之后才发现是 `SKIP`（少见）→ 撤回。「跑完了一句正文都没有」不算 SKIP：都动过工具了，话题站得住，撤回反而是噪音。

模板配了判定的话，大部分闲聊在判定那一步就挡掉了（[judge.md](judge.md)），这里是第二道。

@机器人 不走这套：找机器人就是要它回，**一收到就发**。

## 话题回复

群里的卡片回在那条 @ 消息的**话题**里，不刷主楼（`--reply-in-thread`）。私聊没有话题，不带这个参数。

发卡片带 `--idempotency-key card-<身份>-<消息 id>`，同一条消息重试不会回出两张卡。

## @我：整卡 PATCH

我本人发的卡片用不了 CardKit（只认机器人身份），只能整卡替换：`PATCH /open-apis/im/v1/messages/{id}`（CLI 没封装这个接口，走 `lark-cli api`）。

- **节流 1.2 秒**：CC 事件很密，全推会撞频控。
- **所有刷新串成一条链**：不会并发 PATCH 同一条消息（慢的时候乱序回来，卡片会闪回旧内容）；`finish()` 等到的是「这一帧真写完了」，不是「排上队了」。
- 链上只留**最新**的一帧：中间态漏几帧无所谓，下一帧就追上了；但**收尾那一帧绝不能丢**。丢了的话群里那张卡片永远停在「处理中…」，而 web UI 走 SSE 照样显示完成，两边对不上，还只有群里的人看得见。
- 单次 PATCH 失败只打日志，刷不上去不该弄死这次运行。

## 布局

按飞书卡片的视觉规范排层级：一个焦点，次要信息收进折叠框。

| 位置 | 内容 | 样式 |
|---|---|---|
| 头部 | `⏳ 处理中…` / `✅ 已完成` / `⚠️ 已中断`，副标题「谁 @你」 | 蓝 / 绿 / 橙，群里扫一眼颜色就知道结果 |
| 顶部 | 原问题 | 引用 + 小一号 + 灰色 |
| 正文 | 结论的**第一段**（开头是标题就带上它下面那段，最多 300 字），流式 | 正常字号，唯一焦点 |
| 折叠框 | **完整结论**：全文。一段话就说完的不折，原样露在正文位置 | 默认收起 |
| 折叠框 | **过程 · N 次工具调用** | 思考是灰色引用块，工具名是 `<text_tag>`，入参是 inline code，返回原文进代码块 |
| 底部 | `session <id>` | 小一号 + 灰色 |

- **思考和工具调用在同一条时间线上，不拆两个框**：它们是「看到报错 → 想到查 X → 调 Bash → 返回 → 想到 Y」这条因果链的两半，拆开就得让读的人自己在脑子里拼回去。
- **默认全收起**：群里不只提问的人在看，扫一眼结论就够；想看全文、过程自己点开。跑的时候也收着。
- 露出来的那段不含代码块：掐一半的 ` ``` ` 会把卡片后面全变成代码。一上来就是代码的，只剩折起来的全文。
- 措辞**不跟场景绑**（「处理中」而不是「排查中」）：模板配成什么它就是什么，不只用来排查问题。
- 工具入参只挑一个最能说明「在干嘛」的字段显示（`command` / `file_path` / `pattern` / `query`……）；单条工具返回截到 500 字。

**@机器人的卡片按时间顺序取内容**（`CardBuilder.chrono`），布局跟 @我 的一样。正文只留**最后一段话**，中途「我先看下日志」这种过场话挪进过程。过程是精简版：每段思考只留开头一行（100 字）、不放工具输出（全文在 web UI）。CC 一次排查的思考能有上百 KB，整卡只有 30KB。

## 30KB 预算

飞书对卡片 JSON 的**硬上限是 30KB**，超了接口直接拒收。没有子卡片或嵌套组件能绕开它：折叠面板只是视觉上收起，payload 一样大。

所以按**字节**（不是字数：中文一个字 3 字节，转义出来的 `&#60;` 一个字符占 5 字节）给整张卡留 24KB，剩下 6KB 给外层 `{content: "<转义过的卡片>"}` 那层：

1. 过程先按 8KB 上限裁：正文短的时候它也别长成流水账。
2. 一起塞得下就原样出，绝大多数卡片走这条。
3. 塞不下：**正文先吃满**，过程吃剩下的；剩不到 600 字节就把过程换成一句「正文较长，过程已省略」（面板标题里还留着「N 次工具调用」）。

实测正文中文能到约 8000 字，ASCII 约 24000 字。

**截断方向跟着状态走**：跑的时候留尾部（看最新在干嘛），收尾留头部（结论在前）。机器人卡片的过程始终留尾部：最后几步离结论最近。按字节裁会在 UTF-8 字符边界上退，不会把汉字切成半个。

一张卡最胖的那一帧超过预算 80% 时，收尾会打一条 `card near limit: peak NB body=NB process=NB`，一次运行最多一条。日志里长期没有这条，就说明预算够用，不用去做「正文拆成多条消息」那套（30KB 是单条消息的上限，只有拆消息才能突破）。

## markdown 转义

飞书卡片的 markdown 是真的会解析的：思考里的 `a_b_c` 会变斜体，`<T>` 会直接消失，单独一行的 `---` 会变分割线，工具入参里的 `---FILE TYPE---` 会横插一条线。所以内容里的 `* _ ~ \` > < [ ] #` 和连续三个以上的减号都转成数字实体（`esc()`），渲染出来还是原字符。工具返回里自带的 ` ``` ` 会被剥掉，不然会把外层代码块提前闭合。这个坑踩过一次，现在有测试盯着。

## @机器人：CardKit 流式

机器人的卡片能流式（打字机效果），我的不能，因为 CardKit（卡片实体 + 流式更新）**只认机器人身份**（tenant token + `cardkit:card:write`）。

`KitStream` 的流程：

1. **开**：建卡片实体（`streaming_mode` 开着）→ 按 `card_id` 回复出去。
2. **跑**：把卡片拆成「骨架」（除正文和过程两块之外的所有东西）和两块文本。骨架没变，就只往正文 / 过程两块里写**全量文本**：旧文本是新文本的前缀，新增那段就以打字机效果打出来。骨架变了（面板出现、session 那行出现……）才整卡替换。节流 400ms（流式接口不受消息 PATCH 那种频控）。
3. **收尾**：先关流式，再整卡写最终帧。失败隔 1.5 秒重试，最多三次：收尾帧丢了卡片就永远停在「处理中」。

细节：

- CC 的事件是**整段**来的（没开 partial messages），所以「流式」是每段以打字机效果出来，不是逐 token。最显眼的是最后那段结论：它通常在最后一次工具调用之后一整段出来。
- 打字速度调到约 150 字/秒（默认 70ms 一个字，一段长结论要打两分多钟）。新内容来了，上一段没打完的直接上屏，不排队。
- 跑的时候面板标题**不写工具次数**：次数一变骨架就变，得整卡替换，正在打的字会被打断。收尾那帧补上。
- 流式模式开 10 分钟会自己关（CC 跑久了常见），之后打字报 `300309`，重新打开接着写。
- 同一张卡片上每次操作的 `sequence` 必须严格递增，所以所有写串在一条链上。
- **CardKit 建卡失败就退回普通卡片**（`CardStream` 那套整卡 PATCH），机器人不会因此不吭声。

## 卡片上不放按钮

按钮（终止、追问输入框都一样）要另外订阅 `card.action.trigger` 回调，配置麻烦，收益不大。终止在 web UI 上点，追问直接回消息（见 [session.md](session.md)）。

## 没有确认闸门

卡片一旦开出去，CC 的输出就边跑边写进去：群里不用干等，但**内容在「确认」之前就已经进群了**。想回到「确认后才发」，那份实现在 `git show 53b1657:src.bak-confirm-flow/`（删掉之前原样提交过一次）。安全上的含义见 [security.md](security.md)。
