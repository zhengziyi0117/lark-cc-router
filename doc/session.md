# 追问和 session

每次排查是一个 `claude -p` session。session id 贴在卡片最底下，同时记进库里，下次有人接着问就 `--resume` 它，不用从零重查。

## 锚点

一条消息能不能接上之前的 session，看它带不带**锚点**（`anchorOf()`）：

1. **话题 id**（`thread_id`）：群里在那张卡片的话题下再 @。
2. **引用的消息 id**（`reply_to`）：引用那张卡片再 @。

话题优先。两个都没有 = 新问题、新 session，哪怕同一个会话里还有别的在跑，各跑各的。

所以卡片开出来时**记两个锚点**（`rememberThread()`，写进 `threads` 表）：

- **卡片自己的 message_id**：直接记，不依赖飞书。
- **话题 id**：发 / 回消息的接口只返回 message_id，**只有 mget 带 `thread_id`**，所以要拿卡片 id 再问一次。这一步失败只打日志：卡片锚点已经记上了，最多是群里的追问从零重查。

**私聊为什么靠引用**：私聊没有话题，实测 `thread_id` 恒为空，引用是唯一的线索。没有它，私聊的追问全都会被当成新问题；而引用的原文又不在 `content` 里，模型看不到，只会回一句「哪个？」。实测「hello.txt 里 magic number 是多少」→ 4217，追问「把这个数字乘以 2」→ 8434，没有重读文件。

**卡片一开出来就记**，不等跑完：跑着的时候话题里就可能有人追问，得能对上这个 session。@我 开卡片时 session 早就有了（开闸要等模型开口）；@机器人 卡片先发，等 init 事件拿到 session 再记一次。

## 规则一览

| | 接着问 | 新问题 |
|---|---|---|
| 群里 | 在那张卡片的**话题里** @ | 群里直接 @ |
| 私聊 | **引用**那张卡片再 @（@机器人 的私聊不用 @） | 不引用 |
| web UI | 作业上的「接着问」 | 「试跑」 |

群里 / 私聊来的作业点「再跑一次」：把原消息按原入口再处理一遍，等于这条消息重新进来一次（不判定），所以照上面的规则走 —— 原消息挂在话题里、或者引用了卡片的，接着那个 session（跑断了的接着跑）；都没有就是新 session。

追问在判定的输入里会标成「是追问」，默认提示词里追问默认 `answer`：「这个是线上环境的」「把范围扩大到 10 月」这种短句也是有效追问。

接着问的时候，话题里**上次之后**的新消息会补给它（[intake.md](intake.md#话题上下文)）。

## 追问进来时上一次还在跑：掐掉，接着问

不是排队等它跑完，也不是并排再起一个。相当于 CC 又收到了一条消息（Ctrl+C 之后接着说）。

能这么做是因为 **session id 在 `init` 事件里第一秒就有**，不用等跑完：

1. SIGTERM 掉 `claude`。实测它正在跑的工具子进程跟着一起死，不留孤儿。5 秒还不退就 SIGKILL，因为接棒的那条在等它。
2. 等它把卡片和库收干净（`InFlight.settled`），名额还回池子。
3. 追问 `--resume` 同一个 session。

**实测掐在工具执行中间也没事**：resume 回来还记得上一轮问的是什么，session id 也不变。

- 被打断的那张卡片收尾成「⚠️ 已中断」+ 一行说明（「来了追问，接着往下问」），**不算失败**。
- 判据是 **session**（`inflight` 按 session id 索引），不同 session 互不影响。新开的 session 在 init 时也挂上去，所以第一次问还在跑时来的追问也能接棒。
- **还在排队、没开跑的不掐**：掐了等于吞掉它那句话（用户看到的是「我问了它没理」），追问就排在它后面等它跑完。
- 同一个 session 连来两条追问：后来的挂上去顶掉前一条，永远是链上最新的那个在跑。
- **判了不回的不掐**：「谢谢」不该把正在查的打断。判定在接棒之前做。

## session 不在了

session 被清理了、或者换了机器：`claude --resume` 会报 `No conversation found`，连 init 都不发，直接退出。认出来的标志是「这次跑一个事件都没产出」（`stream.silent`）。

这时把这个锚点的映射删掉（`dropSession`），**从零重跑一次**，并带上完整的话题上下文。不这么做的话，这个话题会永远撞同一堵墙：每次追问都失败，还查不出原因。

被掐掉的那次也是「没产出事件」，所以先判是不是被掐了，被掐的不算「不在了」。

## 其它中断

被掐的原因都写进卡片和库：

| 原因 | 卡片上的说明 | 库里的 error |
|---|---|---|
| 来了追问 | 来了追问，接着往下问 | 被追问打断 |
| 判定为 `stop` | 被叫停了 | 被叫停 |
| web UI 点「终止」 | 已手动停止 | 后台终止 |
| 服务停止 | 服务重启了，这次没跑完 | 服务停止 |

### 停机

Ctrl+C（SIGINT / SIGTERM）时 `drain()`：掐掉所有作业（含排队的），等它们把卡片收成「⚠️ 已中断」再退，最多等 10 秒。不等的话 `process.exit` 会抢在收尾那帧之前，群里的卡片永远停在「处理中…」。再按一次立刻退出。

`drain()` 要在信号处理里**同步**调：Ctrl+C 的 SIGINT 同时打到 claude 子进程，得赶在它们退出前把「被掐了」立起来，不然会被当成「跑挂了」。

退出时显式关掉 web server 和所有 SSE 长连接：不关的话这些 handle 会一直撑着事件循环，进程打印完 `stopped` 却不退，留个孤儿占着端口，下次启动就 `EADDRINUSE`。

进程被硬杀的话，库里会留下 `running` 状态的作业，下次启动时改成 `failed / 进程中断`。

## 并发

`Pool` 是进程内的并发闸，两个入口共用 `maxJobs` 个名额（跑的是同一台机器上的 CC）。web UI 上改上限立即生效：调大立刻放排队的进来；调小不掐在跑的，等它们自然还名额。
